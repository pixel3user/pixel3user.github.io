Game Development

Game engines and interactive 3D

Gameplay systems engineering for networked play, where correctness means every client agrees with the server and performance means the server still ticks on budget at peak combat. The work spans ability architecture, replication design, AI, and systematic profiling with Unreal Insights.

Tools surveyed in this file: Godot · Defold · Solar 2D · Panda 3D · Open 3D Engine (O3DE) · Stride (Xenko) · LibGDX · Cocos2d-x · Three.js Editor

How this page is organised: engineering decision first, visual mechanism second, claim-by-claim audit third, and the retained files that would settle the claim last.

The engineering decision

Can sixteen players share fast combat state that feels local, cannot be forged by a client, and still fits a 60 Hz server tick?

This question — not the software logo list — is the organising test for the case. Every visual and artefact below either helps answer it or exposes what is still only an assertion in the survey text.

Failure modes worth probing

  • A cosmetic cue is replicated reliably to everyone and quietly becomes the largest bandwidth consumer.
  • Client prediction applies cost/cooldown differently from the server, causing visible rubber-banding on ability use.
  • EQS queries spike when many AI share a stimulus, even though average tick time looks healthy.
  • Relevancy distances tuned for one arena cause pop-in or stale enemies in larger spaces.

Three questions that reveal depth

  1. Which state is predicted, which is interpolated, and which is never trusted from a client?
  2. What scenario produced the 35% and 4.2 ms figures, and can it be rerun headlessly?
  3. What happens to abilities in flight when a player disconnects or an actor goes dormant?

Execution sequence

16-player networked action gameplay in Unreal Engine 5

The source brief in delivery order, rewritten as an inspectable process. Each step should leave behind one of the artefacts in the dossier above; a step with no surviving output is where a reviewer should press hardest.

  1. Architect for the network first

    Design core multiplayer systems for up to 16 concurrent players per session, with synchronisation rules decided before features are built on top of them.

  2. Build abilities on GAS

    Implement modular combat abilities and attribute sets in C++ with the Gameplay Ability System, keeping authority on the server so clients cannot forge game state.

  3. Spend bandwidth deliberately

    Tune actor replication rules, custom struct net serialisation, and reliable RPC pipelines — reducing network bandwidth overhead by 35% without changing how the game feels.

  4. Synchronise the AI

    Drive enemies with Behaviour Trees and the Environment Query System, with replicated perception so every client sees the same combat reactions at the same time.

  5. Profile, then optimise

    Hunt bottlenecks in Unreal Insights, cutting server tick time by 4.2 ms and locking a stable 60 FPS under peak combat load.

Expected deliverables

  • C++ GAS ability and attribute-set architecture
  • Replication design: relevancy, serialisation, RPC map
  • AI behaviour trees with EQS queries
  • Unreal Insights traces before/after optimisation

How quality is validated

  • Bandwidth per player reduced 35% after serialisation pass
  • Server tick reduced by 4.2 ms, measured in Insights
  • Stable 60 FPS at peak simulated combat load
  • Playable feel retained under simulated latency
